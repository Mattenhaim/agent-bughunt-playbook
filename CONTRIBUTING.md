# Contributing

Thanks for reading — and doubly so if you want to improve the playbook.

## Fixing or extending content

1. Open an issue first (use the **Feedback** template) if the change is substantive — a wrong claim, a missing failure mode, a better prompt.
2. Small fixes (typos, broken links, clearer wording) can go straight to a PR.
3. PRs: one topic per PR, `docs:` prefix in the title, and a line in the body on *why* the change makes the playbook more accurate — this repo's whole point is not overstating anything.

## Ground rules

- **No secrets, no personal emails, no absolute local paths** in commits or content (see [`playbook/09-security-checklist.md`](playbook/09-security-checklist.md) for the grep list).
- **No unverified case studies.** A case study must reference a real, linkable PR or issue, and its status must be live-checked at the time of writing.
- **Respect target projects.** Keep code excerpts from other projects short and linked; don't mirror their code here.
- The [MIT license](LICENSE) covers this repo; linked PRs/issues belong to their respective projects.

## Running the playbook yourself

Start at [`playbook/01-choosing-a-target.md`](playbook/01-choosing-a-target.md) and the [5-minute quickstart](README.md#5-minute-quickstart-run-a-round-on-a-new-repo). If your run produces a better failure mode for the playbook to warn about, that's exactly the kind of contribution we want.
